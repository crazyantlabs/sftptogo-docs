# SFTP To Go Documentation

This is the documentation site for [SFTP To Go](https://sftptogo.com), built with [Docusaurus 3](https://docusaurus.io/).

## Commands

- `yarn install` — Install dependencies
- `yarn start` — Start local dev server
- `yarn build` — Production build (fails on broken links/markdown)
- `yarn gen-api-docs` — Regenerate the API reference pages in `api/` from `static/openapi/management.yaml`

## Project structure

- `docs/` — Markdown documentation files (the guides sidebar is generated from its directory structure)
- `docs/*/_category_.json` — Sidebar category labels and ordering
- `api/` — The API reference at `/docs/api/`, generated by `yarn gen-api-docs` (`docusaurus-plugin-openapi-docs`). A separate docs instance whose sidebar (`sidebarsApi.js`) is the generated `api/sidebar.ts`, in the spec's tag order, with the hand-written pages added. Never edit the generated files by hand. `api/authentication.mdx`, `api/errors.md` and `api/pagination.mdx` are hand-written; `src/theme/ApiExplorer/Request/` adds the live-organization warning above the request panel, and `src/theme/ApiExplorer/Response/` explains a request that failed without a status code
- `scripts/api-reference.js` — What the API reference's code shares: the docs instance's id, folder and route, the spec path, the pricing URL, the hand-written pages and the sentences that link them. Change these there, once
- `scripts/api-page-markdown.js` — Renders operation pages for the generator, adding the plan box from the spec's `x-plan`; `scripts/api-info-page.mustache` — the introduction's template, which serves it at `/docs/api/introduction` (its closing links come from the info-page generator); `scripts/postprocess-api-docs.js` points each operation's Authorization box at the Authentication page, empties the request panel's pre-filled values and strips Markdown from page descriptions
- `src/theme/ExploreWithAI/` — The "Explore with AI" menu (open the page in an AI assistant, copy it as Markdown), reusable on any page: `<ExploreWithAI prompt="…" markdownUrl="…" />`. Its assistants match the homepage's "Ask AI about SFTP To Go" and send the same `Ask AI Clicked` event. `src/theme/DocBreadcrumbs/` places it on API reference pages
- `plugins/api-markdown/` — Writes a Markdown copy of every API page at build time, served at `<page URL>.md`
- `static/openapi/management.yaml` — The bundled Management API spec, copied from the api repo; served at `/docs/openapi/management.yaml`
- `src/` — React components, theme overrides, and custom CSS
- `static/` — Static assets (images, favicon)
- `docusaurus.config.js` — Site configuration (navbar, footer, plugins, search)
- `sidebars.js` — Guides sidebar (autogenerated); `sidebarsApi.js` — API reference sidebar

## Writing conventions

- Use sentence case for headings (e.g., "Setting up a custom SFTP server name")
- Use numbered lists for sequential steps, bullet lists for non-sequential items
- Use Docusaurus admonitions: `:::info` for plan-gated features or important notes, `:::note` for tips, `:::warning` for potential pitfalls
- Plan-gated features should include an `:::info` block linking to the [pricing page](https://sftptogo.com/pricing), e.g.:
  ```
  :::info
  This feature is only available with certain plans. Read more about our different plans [here](https://sftptogo.com/pricing)
  :::
  ```
- Use relative markdown links between docs (e.g., `[link text](../getting-started/organization-settings#domains)`)
- Wrap UI element names in bold (e.g., click **Add domain**)
- Use backticks for code, CLI commands, and file paths
- Keep instructions concise and action-oriented (imperative mood: "Click", "Enter", "Select")
- Write guides as `.md`. Use `.mdx` only when a page needs a component, such as tabs (`import Tabs from '@theme/Tabs'` and `import TabItem from '@theme/TabItem'`, with a `groupId` so the reader's choice carries across pages). The files in `api/` are generated, except the hand-written `authentication.mdx`, `errors.md` and `pagination.mdx`: fix generated content in the spec, then regenerate
- On API reference pages, a plan requirement comes from the spec: an operation's `x-plan` extension (`feature`, optionally with `appliesTo`, and/or `limit`) becomes the same `:::info` box with the pricing link that guides use
